Editing and validation boundaries¶

Ufor models are field-frozen, not deeply immutable. Lists and dictionaries remain editable authoring values. Editing their contents does not run model validators; neither does Pydantic's model_copy(update=...). A validated object can therefore become invalid after an edit. This behavior is intentional for authoring.

Loading through the codec validates the document. score_toml revalidates the current contents before serialization. JSON model dumps alone serialize values; validate the result when loading it. TOML has no null array element, so a score containing a decoded OSC null argument is rejected by score_toml with a specific error. JSON preserves that positional argument without loss.

Library normalization validates resolved scores. Composition revalidates and copies supplied score records, including their nested collections, into its own registry. Resolving inline scores never adds entries to the caller's registry. Sample and synth preparation revalidate the instrument before making lifecycle decisions. Callers must not mutate these prepared records during their use.

Low-level reference calculations take valid definitions as a precondition. After editing a definition, validate its dumped contents using its model class before calling these calculations. They do not recursively revalidate on every scalar observation. Derived musical values are calculated from current contents rather than cached, so valid edits remain visible.

Public functions do not promise safe concurrent mutation. Author, validate, then evaluate or prepare; maintain runtime state separately from the definition.

Recursive composition models support direct construction, validation, and schema generation from their defining modules. Their model rebuild loads the supported score union from ufor.score_types only when needed; callers need not import ufor.codec for initialization. This applies to Part, arrangement models, and light animation models.

Schema and semantic validation¶

schema/scores.json, generated by ufor.codec.score_schema, describes the structural envelope and many scalar constraints. Passing JSON Schema is necessary but not sufficient for acceptance. Cross-field validators, custom text rules, and reference-dependent checks are also normative. Implementations must apply them after structural validation; schema defaults do not resolve inherited settings or normalize selectors by themselves.

Asset is a source declaration, not an acquired payload or a promise that the bytes are currently available. Assets use one discriminated location object. The source determines which facts are legal:

Location Required content identity Audio extent Access
relative_file, volume_file, download, git_file content with optional measured byte length and SHA-256 Required for audio Finite random access after resolution
stream Forbidden Optional Sequential unless the host reports seeking
Python buffer provider Forbidden Required Random access in the returned array
Python callback provider Forbidden Optional Provider-owned sequential push
Python client_buffer provider Forbidden Optional Client-owned sequential pull

Relative and volume/Git member paths are portable POSIX paths below their declared root. Downloads require an absolute credential-free HTTPS URL and no fragment. Git locations require an absolute supported repository URI, a full lowercase object ID, and a portable blob path. Stream URLs are absolute and credential-free. Provider modules are dotted Python names, functions are Python identifiers, and arguments contain recursive finite JSON values only. Provider arguments are limited to 10000 values and 64 nesting levels. parse_score accepts at most 16777216 TOML characters, 100000 decoded values, and 64 decoded nesting levels; larger documents fail validation.

Validation grants no authority to read a volume, open a network connection, contact Git, import Python, or decode media. Hosts resolve those declarations under explicit policy and compare observed facts with the score before use. Ufor performs no acquisition while parsing, validating, or generating schema. Finite source types describe materializable output, but a Python buffer provider has no pinned byte identity until a host materializes it.

Score version 4 introduces structured locations. codec.migrate_score_v3 accepts a decoded version 3 score, converts its relative path, byte_length, and sha256 asset fields to location and content, advances the version, and validates the result. It does not mutate the supplied dictionary or overwrite a file. Version 4 models do not accept the removed fields.

Identifiers deliberately preserve Unicode. For each code point, the first must have the Unicode Lowercase property; remaining code points must have Lowercase, Numeric_Type Decimal or Digit, or be ASCII - or _. This matches Python's single-character islower and isdigit predicates. There is no normalization, case folding, transliteration, or locale-dependent comparison. Thus é2 and a² are valid, while uppercase letters and decomposed combining marks are not. Consumers must agree on Unicode property data for newly assigned characters; the conformance file pins examples of accepted and rejected existing characters. Identifiers are not the same type as library/score display names.

Literal selectors have separate rules:

  • Library names are nonempty, trimmed and contain no :, #, or /.
  • Score names also reject .*. Internal spaces remain literal.
  • A tag starts with # and has a nonempty value containing no whitespace, :, #, or /. Repeated tags are deduplicated in first-occurrence order.
  • Addresses start with /, reject :, #, and backslashes, and have nonempty, trimmed components other than . or ...
  • Selector parsing trims the surrounding library, name, tag and address pieces; it does not interpret a regex, shell glob, or quoting language.

The remaining semantic rules are grouped by their defining format documents:

Domain Required checks beyond basic shape
Composition Unique IDs, one reference selection, existing public targets, acyclic graphs, single input writers, compatible clocks/layouts, exact integer conversion and parameter-domain narrowing
Instruments Existing asset/group/selection/control references, effective inherited settings, spatial layouts, legal trigger mappings, choke/sustain/articulation contracts and supported preparation profile
Modulation and automation Ordered points/events, valid domains, scope/unit compatibility, writer combination and envelope/LFO time/polarity constraints
Bindings Complete numeric domains or enum tables, monotone endpoint-covered piecewise mapping, distinct native targets and existing stream references
Fixtures Matching parameter/encoding domains, complete choices, distinct slots, valid cue values and noncolliding physical footprints
Slideshow and broadcast Existing assets/sources, adjacent unique transitions, effective cue rules, caption language, acyclic timing dependencies and ordered run events
Musical definitions Positive pitch expressions, finite/repeating table bounds, strict interval input and the explicitly permissive Scale editing contract

These rules apply to decoded values, not just one wire syntax. Portable rejected examples live in validation.json; they are representative boundary cases, not an exhaustive substitute for the format rules. Shared lifecycle examples live in instrument-lifecycle.json. The Python tests consume the same examples as a reference for other implementations.
